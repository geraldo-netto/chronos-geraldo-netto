| T762 | performance; memory and CPU management | Medium | open | M | Coalesce the change signals across a queued run of event mutations, not just within one. | **[found 2026-08-06 by rescan]** `cinnamon-calendar-server.py`'s `recurrence_generated` calls `emit_events_added_or_updated(calendar, [event])` **once per generated instance**, so one weekly meeting inside the 42-day window arrives as six separate `events-added-or-updated` signals, and a work calendar with a dozen weeklies arrives as roughly seventy. Each becomes its own entry in `_event_mutations` (`eventsManager.js:253`), each drains on its own `Mainloop.idle_add` turn (`_schedule_event_mutation`), and each is a one-event mutation — so `_apply_add_mutation` computes `last = end >= mutation.events.length` as true on its first and only chunk and `_apply_added_or_updated` flushes `_pending_emit` every time. The header comment above `_handle_added_or_updated_events` states the intent this misses: "What changed is accumulated across the chunks and said once, at the end" — true within one signal's chunks, not across a queued run of signals. The grid half is absorbed downstream (`calendar.js:_events_updated` coalesces onto one idle through `_queue_update`), but `selected-date-events-changed` is delivered synchronously to `AppletMenuBuilder._renderAgenda` on every one of them, so the event column pays a `setEvents` per instance: an index lookup, `setOverflowed`, and either a `refreshTimeState()` pass over every row or a full teardown/rebuild when the selected day's `EventDataList.timestamp` moved. Hold `_pending_emit` when the mutation behind the current one is another `add` and flush at the end of the run instead — the accumulator is already there, only its flush boundary is wrong. Verify against a burst of single-event mutations, and keep the existing per-signal flush behaviour for a queue whose next entry is a `remove`/`resync`/`fetch-complete`, which must stay ordered against the emit. |

## Recorded decisions

| id | decision |
|----|----------|
| D01 | Keep the third-party endpoints rather than a bundled data set or a single vendor. A bundled table goes stale and covers fewer countries; a single provider breaks whenever it is down — the fallback chain exists because the primary is a hobbyist service. Risk accepted with mitigations (weather opt-in; one-time local-tzdata holiday default with visible third-party disclosure and explicit disable/override; size caps; bounded spans; shape checks in and out of cache; colour filtering; no URL logging). |
| D02 | **Keep the widened export surface.** ~80 exported names have no cross-module consumer — used inside their own file and otherwise only by `test/`. The applet runs inside a compositor where a bug costs the whole session; testing only through the composition root would be slow and flaky. **This does not license the inverse:** production must not bend to a test double's shape. |
| D03 | **`author` is the display name "Geraldo Netto", not the GitHub handle.** `info.json`/`package.json` use "Geraldo Netto"; `schema_static.test.js` asserts it. The Spices convention prefers the handle, but the display name is the maintainer's explicit choice. |
