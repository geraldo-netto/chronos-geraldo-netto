| T699 | state machine integrity; runtime-contract correctness | High | open | M | Do not treat the `SetTimeRange` acknowledgement as completion of calendar-event delivery. | **[verified]** `EventsManager.call_finished()` enqueues `fetch-complete`, whose application immediately culls every entry older than the request watermark (`eventsManager.js:487-496,616-645`). Cinnamon's server instead starts each calendar's asynchronous `get_view()` and completes the D-Bus method immediately (`/usr/libexec/cinnamon/cinnamon-calendar-server.py:245-270`); the view is only finished, connected, and started later (`:277-317`), and the initial event signal is emitted later still (`:318-389`). A successful forced refresh can therefore erase the current rows/dots before a delayed non-empty snapshot arrives, and a view that fails after the acknowledgement is indistinguishable from a successful empty result. Separate “request accepted” from delivery quiescence, retain last-known data through view failure, reconcile after a bounded signal-quiet window, and cover delayed non-empty, genuinely empty, and post-acknowledgement failure paths. |
| T700 | state machine integrity; data consistency | Medium | open | S | Reject causally older calendar-event updates that arrive after a newer revision. | **[verified]** every added/updated signal is stamped with whichever request watermark is current when the signal happens to arrive (`eventsManager.js:233-260`), while `EventIndex._prepareEvent()` replaces an existing UID without comparing the EDS `modified` value already carried by `EventData` (`eventIndex.js:125-135`; `eventData.js:124-171`). The installed server can overlap views during rapid range changes: it replaces a shared `calendar.view_cancellable`, but the old asynchronous callback later checks that shared current field rather than its originating cancellable before starting its view (`/usr/libexec/cinnamon/cinnamon-calendar-server.py:277-316`). An older snapshot can consequently arrive after the replacement, overwrite a newer event in an overlapping date window, inherit the new watermark, and survive GC. Enforce per-UID revision ordering before rewriting buckets and cover out-of-order updates across superseded range/force-refresh requests. |
| T701 | fallback state machine; correctness | Medium | open | S | Prefer an authoritative empty holiday result over an earlier provider failure. | **[verified]** the fallback chain deliberately records a valid empty payload and continues (`holidayAdapters.js:77-95,143-151`), but `tryProvidersInOrder()` retains the first rejected result as `failure` (`providerUtils.js:103-123`) and exhaustion selects `failure || emptyResult` (`holidayAdapters.js:103-109`). If one provider fails and a later provider validly reports no holidays, the failure wins: the holiday-free year is surfaced as unavailable, is not cached as authoritative, and stays on the short failure retry cadence. Reverse that outcome priority while still trying every provider, preserve the successful empty provider's provenance, and cover failure-then-empty plus all-empty chains. |
| T702 | source attribution; wiring congruence | Low | open | S | Aggregate holiday-provider attribution across every month in the visible grid pass. | **[verified]** a 42-day grid may request months from two calendar years, each with an independent cached status/provider (`holidays.js:556-599`; `5.4/calendarAnnotations.js:345-377`). The annotator owns only one provider string and ignores successful siblings until `_awaited` reaches zero, so the last callback alone supplies the month header's provider credit (`5.4/calendarAnnotations.js:286-297,330-341`). When adjacent years are served by different fallback providers, holidays from both appear but only one source is announced; completion timing chooses which one. Collect distinct successful provider names (and the provider attached to any retained error) in the pass, then render deterministic attribution for the complete grid. |
| T703 | state machine integrity; async race / wiring | Medium | open | S | Invalidate panel-weather work immediately when the active location changes. | **[verified]** `WeatherProvider.queue()` changes the resolved location key but leaves the request generation, periodic/retry timers, and display state intact until the 750 ms debounce calls `schedule()` (`weather.js:204-260`; `weatherScheduler.js:179-188`; `weatherFormat.js:25`). During that window an in-flight callback or old retry remains current, so `_refreshReporter()` can store and paint the previous location's reading and arm more work with the previous settings (`weather.js:262-308`). Invalidate the current request and old-key display state, cancel obsolete retry/periodic work, and expose the new pending/empty state synchronously; debounce only the replacement network dispatch. Cover old success and failure callbacks landing during the edit debounce. |
| T704 | state machine integrity; reliability / resource use | Medium | open | S | Make the weather retry ceiling actually return control to the periodic schedule. | **[verified]** `WeatherRefreshScheduler.retry()` saturates `_retry_attempts` at `MAX_RETRY_ATTEMPTS` but never checks the ceiling before arming another timeout (`weatherScheduler.js:137-163`). `CityWeatherProvider` then logs that it is “falling back to the normal refresh period” when `retriesExhausted()` first becomes true (`cityWeather.js:178-193`), even though every subsequent failure continues the capped retry chain forever; panel weather shares the same scheduler behavior. Because the normal periodic timer is already active, a persistent outage maintains two request streams and the log describes a transition that never occurs. Refuse/cancel retries once the budget is exhausted, rely on the periodic timer until a success resets the budget, and make the scheduler's return/state contract let callers report the transition accurately. |
| T705 | state machine integrity; reliability / correctness | High | open | S | Let the first proxy call D-Bus-activate `org.cinnamon.CalendarServer` instead of treating "no current owner" as a dead server. | **[verified live 2026-08-05]** `busctl --user list` shows `org.cinnamon.CalendarServer` activatable and `/usr/bin/cinnamon-calendar-server` present and working, yet events never come up: after proxy construction `calendarServerConnection.js:110-113` treats `!g_name_owner` as owner loss (`_handle_name_owner_notify` → disconnect → `queueRetry`), so the applet drops the proxy before ever issuing the `call_set_time_range` that would D-Bus-activate the service — the stock applet connects signals with no owner check and lets the first call start the server (`/usr/share/cinnamon/applets/calendar@cinnamon.org/eventView.js:346-377`). Observed: endless 5→300 s backoff loop re-logging "Calendar events supported." every round (`calendarServerConnection.js:64`; 21:52:33→22:08:12 in `~/.xsession-errors`), and the issue footer misdiagnoses "Install or enable Evolution Data Server" while EDS is running (pid owner of `org.gnome.evolution.dataserver.Calendar8`). Keep the owner-loss handling for a server that *had* an owner and died; on the never-started case, publish the proxy and let the first call activate it (the server idle-exits without clients, so expect activation per reconnect). Also log the support line once, not on every retry. |
| T707 | reliability / correctness; state machine integrity | Medium | open | S | Make an in-flight holiday annotation pass survive a calendar grid rebuild between request and response. | **[verified at session start 2026-08-05 21:52:33]** eleven Gjs-CRITICALs on one disposed St.Button (four accesses, seven signal connects — including `new Tooltips.Tooltip` on a destroyed day cell) from the holiday cache's async read callback: `ioUtils.js:107` → `holidayCache.js:253,527,460` → `holidays.js:596,580,713` → annotator. The pass guard `_isCurrent()` compares only `host.holidayGeneration` (`5.4/calendarAnnotations.js:282-283,331`), which does not advance when the grid rebuilds; the LC_TIME locale-query answer lands after first paint and rebuilds the header, dropping all 42 cells and their tooltips (`5.4/calendar.js:690-700`), so the still-current pass annotates destroyed buttons. Advance the generation (or an equivalent pass token) whenever day cells are rebuilt, and add a regression that rebuilds the grid between a `getHolidays` request and its callback. |
| T708 | reliability / correctness; observability | Medium | open | M | Gate weather fetches on network availability and refresh immediately when connectivity returns. | **[verified 2026-08-05]** session start preceded NetworkManager `CONNECTED_GLOBAL` (21:52:37) so every geocoder failed DNS ("Name or service not known"): five failure rounds with full JS stack traces in ~5 s, one per location serialized by the Nominatim queue, then errors displayed until the jittered 30-60 s retry (recovery itself works — verified by driving the real `WeatherProvider`+`CityWeatherProvider`+shared `WeatherReadingRepository` wiring with fake timers and a failing-then-healthy HTTP port; scratchpad repro, and the post-reload instance is healthy). The applet has no `Gio.NetworkMonitor` integration: it burns retry budget and logs error bursts while provably offline, and recovery waits out a blind timer instead of reacting to network-up. Skip/short-circuit dispatch while `network_available` is false (a distinct, quieter "offline" state, not SERVICE_UNAVAILABLE), subscribe to `network-changed` to refresh immediately on reconnect, and keep the existing backoff for genuinely reachable-but-failing services. |

## Recorded decisions

| id | decision |
|----|----------|
| D01 | Keep the third-party endpoints rather than a bundled data set or a single vendor. A bundled table goes stale and covers fewer countries; a single provider breaks whenever it is down — the fallback chain exists because the primary is a hobbyist service. Risk accepted with mitigations (weather opt-in; one-time local-tzdata holiday default with visible third-party disclosure and explicit disable/override; size caps; bounded spans; shape checks in and out of cache; colour filtering; no URL logging). |
| D02 | **Keep the widened export surface.** ~80 exported names have no cross-module consumer — used inside their own file and otherwise only by `test/`. The applet runs inside a compositor where a bug costs the whole session; testing only through the composition root would be slow and flaky. **This does not license the inverse:** production must not bend to a test double's shape. |
| D03 | **`author` is the display name "Geraldo Netto", not the GitHub handle.** `info.json`/`package.json` use "Geraldo Netto"; `schema_static.test.js` asserts it. The Spices convention prefers the handle, but the display name is the maintainer's explicit choice. |
